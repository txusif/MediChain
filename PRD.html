01

Problem statement & goals

⚡
Why v1 failed in production
MetaMask-only onboarding. Required users to install a browser extension, create a wallet, and manage a seed phrase — too high a bar for medical patients and non-crypto doctors.
Polygon Mumbai deprecated. The app is broken for all users. No mainnet deployment means zero credibility.
Stale stack. Thirdweb v2, ethers v5, no account abstraction — all superseded. No Foundry tests for contract correctness.
Single-chain lock-in. One testnet was a student project. Multi-chain mainnet is a professional product.
🎯
v2 goals
Zero crypto prerequisite onboarding. Email, Google, or phone login creates a smart wallet silently. No MetaMask, no seed phrase, no gas fees for the user.
Privacy-correct architecture. Only content hashes go on-chain. Actual files are encrypted on IPFS; Lit Protocol gates decryption to patient-authorised wallets only.
Multi-chain mainnet deployment. Live on Base, Polygon PoS, and Arbitrum One. Users pick their chain; Thirdweb handles switching.
Portfolio-grade proof of work. ERC-4337, Lit Protocol, Foundry scripts, multi-chain deploy — each a concrete signal for Web3 frontend roles.

05

Features & role permissions

🔐
Authentication & onboarding
Login via email OTP, Google OAuth, or phone number using Thirdweb embedded wallets. On first login, a smart account (ERC-4337) is created silently. The user then picks a role (Patient / Doctor / Lab) which is registered on-chain. Thirdweb Paymaster sponsors the registration transaction — user pays zero gas, ever.
📄
Medical record management
Upload (Lab only). Lab selects patient address, uploads PDF/image. Client encrypts the file with Lit Protocol keyed to patient's wallet, uploads ciphertext to IPFS/Pinata, stores CID hash on-chain via addRecord(patientAddr, ipfsCID, fileHash).
View (Patient & authorised Doctors). Patient always can decrypt. Doctor can only decrypt files where patient has called grantAccess(doctorAddr) on-chain. Lit verifies this condition against chain state before releasing the decryption key.
Revoke. Patient calls revokeAccess(doctorAddr). Lit's conditions are re-evaluated on every decrypt attempt, so revocation is immediate.
💰
Crowdfunding campaigns
Any registered user can create a campaign with title, description, target amount, deadline, and IPFS image. All users can donate native tokens to any campaign. CampaignFactory.sol deploys a new campaign contract per creation. Funds auto-release to creator if target met by deadline; otherwise, donors can reclaim (on-chain guarantee, no trusted third party).
06

Smart contracts

PatientRegistry.sol
Manages user registration and role assignment.
registerPatient() registerDoctor() registerLab() getRole(addr) isRegistered(addr)
MedicalRecords.sol
Record storage (hashes only) and access control.
addRecord(patient, cid) getRecords(patient) grantAccess(doctor) revokeAccess(doctor) hasAccess(doctor, patient)
CampaignFactory.sol
Factory pattern — deploys individual campaign contracts.
createCampaign(...) getCampaigns() getCampaignsByOwner(addr)
Campaign.sol
Single campaign instance with fund/refund logic.
donate() withdraw() refund() getState() getDonors()

Foundry deliverables (required for portfolio): test/ with unit tests for all public functions, fuzz tests on donate() and refund(). script/Deploy.s.sol that deploys all 4 contracts to all 3 chains from a single run.

07

Key user flows

🚶
New user onboarding (zero crypto knowledge)
1
User lands on MediChain → clicks "Get started with email"
2
Enters email → Thirdweb sends OTP → user verifies. Smart account created silently in the background.
3
User selects role: Patient, Doctor, or Lab. Paymaster sponsors the registration transaction — user sees no gas fee.
4
Redirected to their role-specific dashboard. No wallet extension, no seed phrase, no ETH required.
📋
Lab uploads a medical report
1
Lab enters patient wallet address, selects PDF/image file.
2
Client-side: Lit Protocol encrypts the file with access condition keyed to patient's address.
3
Encrypted blob uploaded to IPFS via Pinata → returns CID.
4
CID hash stored on-chain via addRecord(). Transaction sponsored by Paymaster.
🩺
Doctor views a patient report
1
Doctor searches patient by wallet address. Contract confirms access is granted via hasAccess().
2
Report list loaded from chain. Doctor selects a record → IPFS fetches the encrypted blob.
3
Lit Protocol verifies on-chain access condition → releases decryption key → file decrypts in-browser. Doctor reads the report.

Non-functional requirements

Privacy & security
Raw medical data never touches the blockchain
All files encrypted client-side before upload
Access control enforced by Lit on-chain conditions
Revocation takes effect immediately (no caching)
No centralised server holds user keys
User experience
First login to dashboard under 30 seconds
Zero gas fees for standard user actions
No crypto wallet extension required ever
Mobile-responsive layout (Tailwind breakpoints)
Skeleton loaders for all async contract reads
Smart contract quality
≥90% line coverage via Foundry tests
Fuzz tests on all financial functions
Re-entrancy guards on withdraw() and refund()
Events emitted for every state change
Verified and published on Etherscan/Polygonscan/Basescan
Multi-chain
Contract addresses config-driven per chain
Chain switching via Thirdweb's built-in selector
Deployed to Base, Polygon PoS, Arbitrum One mainnets
Foundry deploy script is single-run, reproducible
ABI stored in repo, imported in frontend

Portfolio differentiators for Web3 job hunt

ERC-4337 account abstraction in production
Not just understanding the concept — actually shipping gasless email onboarding with a Paymaster. Few junior/mid devs have this. Mention the smart account address in your README.
Lit Protocol for medical-grade privacy
Demonstrates you know that "blockchain ≠ public ≠ private". Decentralised key management is a real interview differentiator. Show the access condition logic in your code walkthrough.
Foundry tests with coverage + fuzz testing
The clearest signal that you take smart contract correctness seriously. Commit your fuzz test failure logs as proof of depth. Most portfolio projects have zero tests.
Scripted multi-chain deployment
A single Foundry script that deploys to 3 mainnets with env-controlled private keys is production discipline. Screenshot the verified contracts page on all 3 explorers for your README hero section.
